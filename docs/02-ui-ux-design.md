# 画像生成プロンプトメーカー Ver.2
# UI / UX設計書 v1.0

## 1. 文書情報

- 対象：image-prompt-maker-v2
- 上位仕様：docs/01-requirements.md
- Version：1.0
- 状態：正式設計

## 2. UIの目的

Ver.2では「プロンプト作成ツールを操作している感覚」を弱める。

ユーザーに「設定している」ではなく、
「自分のイメージを作っている」と感じてもらう。

避けるもの：

- 大量フォーム
- 長い設定一覧
- 専門用語中心の画面
- 管理画面風UI
- 小さな操作部品の密集

目指すもの：

- シンプル
- 上質
- 親しみやすい
- 画像中心
- 十分な余白
- 初心者でも操作したくなる画面

## 3. UX原則

中心コンセプト：

「見て選べば作れる」

操作原則：

「1画面1判断」

基本フロー：

HOME
↓
作りたいもの
↓
絵柄
↓
構図
↓
光・雰囲気
↓
微調整
↓
完成

画面を戻っても、それまでの入力・選択を保持する。

## 4. デザイン方向

DialkitやReadymag等に見られる、

- 大きな余白
- 大きめのタイポグラフィ
- 少数の強いCTA
- 画像中心の選択
- 明確な視線誘導
- ページ自体を体験として見せる

という思想を参考にする。

ただしデザイン・素材・レイアウトをコピーしない。

一般的なAIツールや業務アプリのような見た目を避ける。

## 5. 共通制作画面

基本構造：

[ロゴ / 戻る]

STEP表示

大きな質問
短い補足

メインコンテンツ

[戻る] [次へ]

ただし全Stepを機械的に同じ見た目にはしない。

画像選択Stepでは画像を主役にする。

## 6. HOME

HOMEは説明書にしない。

ファーストビューでは、

- アプリの価値
- 短い説明
- メインCTA
- 視覚的な作品例

を中心にする。

コピー方向例：

「イメージはある。
言葉にするのが難しい。

好きな絵を選ぶだけで、
画像生成プロンプトを作れます。」

主CTA：

「画像を作る」

必要に応じて、
「画像生成用プロンプトを作成します」
等の補足を表示し、
アプリ内で直接画像生成するとの誤解を防ぐ。

MVPでは一枚絵を主役とする。

将来的に、

- キャラクター
- LINEスタンプ
- 保存作品

への入口を追加できる構造にする。

## 7. 作りたいもの

質問：

「どんな画像を作りたい？」

大きめの自然文入力欄を使用する。

例：

- 海辺を歩いている女の子
- カフェでパソコンを使う男性
- 猫が宇宙を旅している絵
- note記事のアイキャッチ

専門的なプロンプト形式を要求しない。

## 8. 絵柄

質問：

「どんな絵にする？」

補足：

「名前が分からなくても大丈夫。
好きな雰囲気を選んでください。」

正式8種類：

1. アニメ風
2. イラスト風
3. リアル風
4. マンガ風（線画）
5. 水彩風
6. 油彩風
7. シンプル・フラット
8. ポップ・かわいい

MVPでは1つ選択を基本とする。

画像＋名称を1つのカードとして表示する。

カード全体をクリック・タップ可能にする。

選択状態は色だけに依存せず、

- 枠
- チェック
- 背景変化
- 軽い拡大

等で明確にする。

## 9. 構図

質問：

「どこまで見せる？」

正式8種類：

1. 顔アップ
2. バストアップ
3. 上半身
4. 全身
5. 引き
6. 横から
7. ローアングル
8. 俯瞰（上から）

「Composition」等の専門用語を覚えさせない。

必要に応じて、

「顔アップ — 表情をしっかり見せる」

のような短い補足を付ける。

## 10. 光・雰囲気

質問：

「どんな空気感にする？」

正式8種類：

1. 自然光
2. 明るい
3. 柔らかい
4. 夕暮れ
5. 夜
6. シネマティック
7. 幻想的
8. ドラマチック

画像＋名称を基本とする。

Lighting等の専門用語を前面に出さない。

## 11. 正式参考画像

正式原本：

images/samples/reference/style-reference.png
images/samples/reference/composition-reference.png
images/samples/reference/lighting-reference.png

3枚とも1536 × 1024 px PNG。

重要：

24枚の原本画像が存在するわけではない。

3枚の比較シートに8種類ずつ、
合計24種類の視覚サンプルが掲載されている。

原本は変更しない。

## 12. UI用画像

実際の選択UIでは、
8種類を個別カードとして表示することを基本候補とする。

個別カードが必要な場合は原本を保持したまま、

images/samples/derived/

等に派生画像を作成する。

原本へ上書きしない。

UI設計書だけを根拠に、
現時点で原本を分割しない。

正式な派生画像仕様は
docs/05-sample-images-spec.md
に従う。

## 13. カードレイアウト

PC：

- 4×2 Gridを第一候補
- 画面幅に応じてレスポンシブ調整
- 画像の違いが判断できる大きさを優先

スマートフォン：

- 2列Gridを第一候補
- 狭い場合は1列も許容
- 横スクロールを必須操作にしない

カード選択だけで自動的に次画面へ移動しない。

選択
↓
選択状態を確認
↓
「次へ」

とする。

## 14. 戻る・次へ

すべての主要Stepで戻れる。

戻っても入力・選択を失わない。

選択必須Stepでは、
未選択時に「次へ」を無理に進ませない。

無効状態の場合は理由が理解できること。

## 15. 微調整

質問：

「もう少しだけ調整する？」

詳細設定画面のようにしない。

MVPでは4軸程度を基本とする。

正式な軸とPromptModelへの変換は、
docs/04-prompt-dictionary.md
で定義する。

UI候補：

- スライダー
- セグメント
- 簡単な選択

数値を意識させすぎない。

例：

「シンプル ───── 描き込み多め」

のように意味で表示する。

## 16. 入れたくないもの

候補例：

- 文字
- ロゴ
- 透かし
- 余分な人物
- 不自然な手
- 不要な小物

チップやcheckbox等の簡単なUIを使用する。

大量のネガティブプロンプト入力を初心者へ要求しない。

## 17. 詳細設定

基本フローに大量の設定を出さない。

必要になった場合のみ、

「もっと細かく調整」

等の折りたたみ領域へ配置する。
## 18. 完成画面

完成画面では、プロンプト文字列だけを突然表示しない。

まず、

「あなたのイメージができました」

という完成体験を作る。

基本構成：

あなたのイメージ

[選択内容のサマリー]

絵柄：水彩風
構図：全身
雰囲気：夕暮れ

[完成プロンプト]

[プロンプトをコピー]

[保存する]

[少し直す]

完成後に最初からやり直さなくても、
各Stepへ戻って編集できるようにする。

## 19. 完成プロンプト

長文でも読みやすい表示にする。

開発者向けコードエディタのような見た目を必須としない。

ユーザーはプロンプト技術者ではない。

完成プロンプトを主役の一つとして扱いつつ、
操作方法を分かりやすくする。

## 20. コピー

完成画面の主要CTAとする。

ボタン：

「プロンプトをコピー」

成功時：

「コピーしました」

と明確に通知する。

スマートフォンでも押しやすいサイズにする。

## 21. AI選択

初期対象：

- ChatGPT
- Gemini
- その他

初心者へ細かなモデルVersionを大量表示しない。

表示例：

「どこで使う？」

ChatGPT
Gemini
その他

内部では、

- ChatGPT Adapter
- Gemini Adapter
- Generic Adapter

に対応する。

## 22. 保存

完成作品を保存できる。

保存時に大量の追加入力を要求しない。

必要なら作品名を自動設定し、
後から変更できる設計を検討する。

新規作品と既存作品の上書きを明確に区別する。

## 23. Draft

制作途中の状態を保持する。

ユーザーがページを閉じたり再読み込みしても、
可能な範囲で復帰できる。

復帰UI例：

「前回の続きがあります」

選択肢例：

- 続きから
- 新しく作る

新しく作る場合でも、
既存Draftを誤って消さない設計を考慮する。

## 24. 履歴

履歴はHOMEの主役にしない。

必要なユーザーが後からアクセスできる位置へ置く。

保存作品と生成履歴はUI上でも区別可能にする。

将来ナビゲーション候補：

- 作品
- 履歴
- キャラクター

## 25. お気に入り

お気に入り操作は簡潔にする。

ハートや星など一般的なアイコンを利用できる。

意味が分かりにくい場合はラベルやTooltipを補助する。

Favoriteの正式対象はデータ設計書に従う。

## 26. キャラクター

キャラクター機能は独立した制作体験として扱う。

一枚絵制作画面に、
大量のキャラクター設定項目を常時表示しない。

一枚絵でキャラクターを利用する場合は、

「キャラクターを使う」

から保存済みキャラクターを選択できる構造を想定する。

## 27. キャラクター作成

将来の基本フロー候補：

キャラクターを作る
↓
基本情報
↓
見た目
↓
性格・雰囲気
↓
基準画像 / 人物ルール
↓
確認
↓
保存

詳細仕様はキャラクター実装フェーズで確定する。

## 28. LINEスタンプ

LINEスタンプは一枚絵とは独立した制作入口を持てる構造とする。

一枚絵フローへ無理に詰め込まない。

同一キャラクターを使って、

- 表情
- ポーズ
- セリフ
- 背景条件

等を選択できる将来構造を考慮する。

## 29. ナビゲーション

MVP初期では複雑なグローバルナビゲーションを作らない。

最低限、

- HOME
- 戻る
- 制作Step
- 保存関連

から開始する。

機能追加に合わせて拡張する。

## 30. ヘッダー

制作中はコンテンツを主役にする。

ヘッダーの高さを取りすぎない。

ロゴやHOMEへの導線を提供する。

保存機能追加後は、
必要に応じて保存状態を表示できる。

## 31. フッター

制作フロー中に巨大なフッターを常時表示しない。

HOMEでは必要に応じて、

- 使い方
- About
- Privacy
- 注意事項

等への導線を設置できる。

## 32. 色

正式カラーパレットは実装段階で確定する。

原則：

- 色数を増やしすぎない
- CTAを明確にする
- カードと背景を識別できる
- 選択状態を明確にする
- 十分なコントラストを確保する

主要CTAと選択状態には、
一貫したAccent Colorを使用する。

## 33. タイポグラフィ

日本語の読みやすさを優先する。

HOMEのメインコピーやStepの質問は大きく表示できる。

小さなフォームラベルが大量に並ぶデザインを避ける。

見出し、本文、補助文の階層を明確にする。

## 34. 余白

余白を積極的にデザイン要素として使用する。

PCでも画面いっぱいに情報を詰め込まない。

ユーザーが次に見る場所が自然に分かる構成とする。

## 35. アニメーション

控えめなアニメーションは使用可能。

候補：

- カード選択
- Step切り替え
- コピー成功
- 完成画面表示

操作を待たせる長いアニメーションは使用しない。

prefers-reduced-motionを考慮し、
アニメーションなしでも操作可能にする。

## 36. スマートフォン

スマートフォンを主要利用環境の一つとする。

特に確認：

- HOME
- 作りたいもの入力
- 2列カード
- 選択状態
- 次へ
- 戻る
- 微調整
- 完成プロンプト
- コピー
- 保存
- Draft復帰

主要フローで横スクロールを発生させない。

## 37. タップ領域

カードは画像の一部だけでなく、
カード全体をタップ可能にする。

主要ボタンには十分なタップ領域を確保する。

小さすぎるアイコンだけを重要操作に使用しない。

## 38. PC

PCでは画面幅を有効活用する。

ただしフォームやカードを横に詰め込みすぎない。

完成画面では必要に応じて、

選択サマリー | 完成プロンプト

等の2カラム構成を利用可能。

プロンプト表示領域が狭くなりすぎる場合は1カラムを優先する。

## 39. スマホ完成画面

スマートフォンでは1列を基本とする。

優先順位：

1. 完成したこと
2. 選択サマリー
3. 完成プロンプト
4. コピー
5. 保存
6. 編集

コピーCTAを押しやすくする。

## 40. アクセシビリティ

最低限対応：

- キーボード操作
- フォーカス表示
- 適切なalt
- 適切なラベル
- 十分なタップ領域
- 色だけに依存しない状態表示
- 基本的なコントラスト

画像選択カードもキーボードで選択可能にする。

## 41. カード状態

ImageChoiceCardは最低限、

- default
- hover
- focus
- selected
- disabled

を持つ。

selected状態は視覚だけでなく、
アクセシビリティ上も認識できるようにする。

## 42. エラー状態

入力・保存等のエラーは、
可能な限り問題が起きた場所の近くへ表示する。

技術エラーをそのまま表示しない。

例：

「保存できませんでした。
もう一度お試しください。」

詳細な技術情報は開発用ログへ分離する。

## 43. 空状態

保存作品や履歴が存在しない場合、
単に「ありません」と表示するだけにしない。

例：

「まだ保存した作品はありません」

＋

「最初の画像を作ってみる」

のように次の行動を提示する。

## 44. ローディング

MVPでは外部AI APIを使用しないため、
長時間の生成待ちは基本的に発生しない。

不要な疑似ローディング演出を入れない。

必要な保存処理等では短い状態表示を行える。

## 45. 画像パフォーマンス

スマートフォンで毎Step、
1536 × 1024の比較シート原本をそのまま大量表示する設計は避ける。

必要に応じてWeb表示向け派生画像を使用する。

正式原本は最適化や上書きの対象にしない。

## 46. 原本と派生画像

正式原本：

images/samples/reference/

UI用派生画像：

images/samples/derived/

のように明確に分離する。

派生画像を作る場合も、
どの正式IDに対応するか追跡可能にする。

## 47. 選択サマリー

制作途中で巨大な設定一覧を常時表示しない。

必要な場合のみ、

「水彩風 / 全身 / 夕暮れ」

のような簡潔な現在選択を表示する。

## 48. 編集

完成後に、

「少し直す」

から選択済みStepへ戻れる。

戻った場合も、
その他の選択を失わない。

## 49. リセット

全入力削除は誤操作しにくい位置へ置く。

データ消失を伴う場合は必要に応じて確認する。

主要CTAの隣に破壊的操作を目立たせない。

## 50. 新規作成

保存後、

「新しい画像を作る」

から新しい制作を開始できる。

既存作品を誤って上書きしない。

## 51. 専門用語

内部ID・PromptModelでは専門語を使用してよい。

UIでは自然な日本語を優先する。

例：

low-angle
→
下から見上げる

high-angle
→
上から見下ろす

内部IDと表示文言を分離する。

## 52. ヘルプ

説明文を大量に常時表示しない。

迷いやすい場所だけ、

- 短い補足
- ?
- Tooltip
- 展開式ヘルプ

等で支援する。

## 53. 初回利用

長いチュートリアルを強制しない。

HOMEからすぐに制作開始できる。

初心者向け説明は必要な場所で短く提示する。

## 54. リピーター

2回目以降は、
説明を毎回読まなくても操作できること。

操作の流れ自体が理解しやすいUIを優先する。

## 55. ログイン

MVPではログインUIを表示しない。

将来GoogleログインやメールOTPを導入する場合も、
制作開始前に必須ログインとするかは改めて検討する。

## 56. 有料機能

MVPでは課金UIを実装しない。

将来有料化する場合も、
制作途中を広告・アップセル等で過度に中断しない。

## 57. 画像生成との誤認防止

MVPでアプリが生成するのは、

「画像そのもの」

ではなく、

「画像生成用プロンプト」

である。

HOMEで「画像を作る」という表現を使用する場合も、
必要に応じて説明を添える。

ユーザーがアプリ内で画像生成まで行われると誤認しないこと。

## 58. 信頼感

MVPでは、

- AI APIキー不要
- 入力をAI APIへ自動送信しない
- 基本データは端末内保存

という特徴を、
必要な場所で簡潔に伝えられるようにする。

HOMEを長いセキュリティ説明で埋めない。

## 59. JSON Backup UI

JSON Export / Importは通常制作フローから分離する。

データ管理画面等から利用可能にする。

Import、全削除等の破壊的操作は通常CTAと区別する。

## 60. 共通UIコンポーネント

共通化候補：

- Button
- Card
- ImageChoiceCard
- StepHeader
- Progress
- TextInput
- Slider
- ChoiceChip
- PromptOutput
- Toast
- Dialog
- EmptyState
- ErrorMessage

実装技術に合わせて調整可能。

## 61. ImageChoiceCard

Ver.2の主要コンポーネント。

最低限保持する情報：

- image
- label
- description（任意）
- selected
- disabled
- internal ID

操作：

- mouse
- touch
- keyboard

に対応する。

## 62. Step State

Step移動時に入力状態を保持する。

UI Stateと永続保存データを密結合しすぎない。

具体的なデータ構造は
docs/03-data-design.md
に従う。

## 63. レスポンシブ

Mobile / Tablet / Desktopを考慮する。

固定デバイス名だけで設計せず、
コンテンツが自然に表示できるbreakpointを採用する。

PCでは適切な最大コンテンツ幅を設ける。

## 64. デザインシステム

初期実装時に最低限、

- spacing
- radius
- typography
- shadow
- border
- color
- transition

をCSS変数等で管理する。

ページごとに場当たり的な値を増やさない。

## 65. ダークモード

MVP必須ではない。

将来対応を不必要に難しくする実装は避ける。

## 66. MVP画面

初期想定：

HOME

CREATE / SUBJECT
CREATE / STYLE
CREATE / COMPOSITION
CREATE / LIGHTING
CREATE / ADJUST
CREATE / RESULT

PROJECTS
HISTORY
DATA / BACKUP

URL構造は実装計画で確定可能。

## 67. MVP後画面

将来：

CHARACTERS
CHARACTER / CREATE
CHARACTER / EDIT
LINE STAMP

必要に応じて追加する。

## 68. UI完成条件

最低限：

1. HOMEから制作開始できる
2. 作りたいものを入力できる

## 69. 正式決定事項

正式決定：

- 1画面1判断
- ステップ型制作
- 画像中心
- 大量フォームを避ける
- 絵柄8種類
- 構図8種類
- 光・雰囲気8種類
- 正式原本は比較シート3枚
- 24枚の原本画像として扱わない
- UIでは個別カード表示を基本候補とする
- 原本を加工しない
- 派生画像は別管理
- PCはGrid
- スマホは2列Gridを第一候補
- カード選択だけで自動遷移しない
- 戻る操作で状態保持
- 完成画面を完成体験として設計
- コピーを主要CTAとする
- 専門用語を前面に出さない
- スマートフォンを主要環境とする
- キャラクターとLINEスタンプは独立体験として追加
